# 当日の手順

## 事前準備

- 3人がPrivateリポジトリをcloneでき、各自のAWS認証で共通ホストへ接続できる。
- 非公開Discordを作り、必要な連携を3人で確認する。
- 過去問でタスク同時取得、候補統合、計測、採用、復旧、接続切断、担当交代を試す。
- 競技の当日ルールでAI・外部サービス・追加ホスト・問題情報の取り扱いを確認する。
- 終了時刻・新規変更停止時刻・最終ベンチの時間枠を人間が決める。
- 現在は競技用ホスト・ソース・ベンチは空。練習用サーバーを自動で競技対象にしない。

## 開始

1. 最初の統合担当を決める。共通ホストの占有・実行中処理・ディスク容量を確認する。
2. 当日公開されたアプリを `app/`、必要な設定を `etc/` に取り込む。秘密鍵・認証情報・巨大データを除き、初期コードをmainにcommitしてpushする。
3. kaizenのsetupで当日マニュアルに基づくpreset、`.kaizen/config.sh`、`.kaizen/RULES.md`を作る。対象ホスト・配備範囲・初期化・build・health・bench方式を明示する。
4. setupの初回配備・復旧ドリルは、環境占有を保持して指定した統合担当がkaizenのsetup手順を実行する。通常ラッパーを有効にする前の、当日一度の明示的な初期化手順とする。
5. 初期ベンチの正しさ・スコア・SHA・条件を取得する。復旧手順を実際に試し、stableを確認する。
6. `.local/target.json`を設定例から作り、rulesと復旧確認をtrueにする。ラッパー経由でstatusとverifyを確認する。
7. 観測資料を共有ホストへ保存する。各AIを起動し、戦略・残り時間・自走範囲を伝える。

## 改善ループ

1. AIが根拠付きタスクを作成・取得し、独立ブランチで実装・検証する。
2. 候補を提出し、他のタスクへ進む。
3. 統合担当は効果見込み・計測時間・リスク・依存関係で候補を選ぶ。完成順に固定しない。
4. 現在のstableへ取り込み、1候補ずつデプロイ・計測・評価する。
5. 通常改善は採用、正しさ違反は復旧、悩ましい候補は人間へ。結果を記録して共有する。
6. 採用で前提が変わったタスクを再確認し、次へ進む。

## 統合担当の交代

採用または復旧済みで、対象操作・ポータルベンチが終了した区切りを使う。`templates/HANDOFF.md`を埋め、後任が実状態を確認する。占有を保持したまま、前任が次を実行する。

```bash
python3 scripts/control.py env-handoff --agent a-codex-01 --token TOKEN \
  --to b-claude-01 --reason 'stable確認済み、実行中処理なし'
```

後任用の新tokenが返る。古いtokenは無効になる。タスクの担当も移す必要があればtask-handoffで明示する。

## 接続切断・処理中断

1. 占有を消さず、SSMのCommand IDとコマンド結果を確認する。
2. 共通ホストの実行中プロセスとローカルprocess lock、競技サーバー各台の配備SHA・health、ポータルベンチの状態を調べる。
3. 生ログとkaizen状態から、終了済み・継続中・部分配備を区別する。SSHやSSMの切断は処理終了の証拠にならない。
4. 継続中なら待つ。部分配備や不明状態なら、事実を揃えて復旧する。正体不明のまま再デプロイしない。
5. 記録を確定してから占有を移す／解放する。自動期限切れやforce解除は用意していない。

## 終了前

- 新たな高リスク変更を止め、未採用候補を配備しない。
- 採用済みstable、配備中SHA、GitHubのmainを照合する。
- サービスの起動・疎通・再起動後の設定保持・ベンチの正しさを確認する。
- スローログ、profiling、debug、一時設定を確認する。観測モードのスコアと通常スコアを混ぜない。
- 再起動試験や最終ベンチは、当日のルールと残り時間に沿って人間が実施順を決める。
- 最終結果・設定・未完了タスクを保存し、全AIへ停止を伝える。
- 共通ホストの状態をバックアップする。不要になった共通EC2は明示的に停止する。競技サーバーの終了は競技ルールに従う。
